# 單店藥局系統｜需求規格與 Roadmap v1

2026-11-15｜範圍：需求收斂、工程順序與驗收；非上線批准。延續 [藥局 Roadmap #37](https://github.com/skydreamer0/startup/issues/37)，不另建一套互相衝突的票。程式核對基準：`startup master d703e416`；PR 與驗收另記版本。

## 1. 產品目標與角色

做一家藥局每天能操作的本地系統：能追「貨從哪裡來、放哪裡、哪一批賣掉／退回、最後如何對帳」。工作台回答現在該做什麼；營運頁回答經營結果。管理人員、門市人員、藥師可兼任，依實際權限顯示任務，既不為角色做三套應用，也不因換介面放寬權限。

| 角色 | 主要工作與畫面 |
|---|---|
| 門市人員 | POS 查找、核對商品／包裝、掛單、結帳；收貨記錄、待核對與上架 |
| 藥師／獲授權覆核者 | 按權限處理批號、效期、隔離、放行或异常；獨立的處方／調劑等實際流程確定後才接，不用假入口 |
| 管理人員 | 工作台例外、庫存差異、交班日結、報表及稽核；設定在次級入口 |
| 顧客 | 顧客顯示是單獨介面，不含員工功能，不誤顯上一筆交易 |

成功標準：好操作、放得下、不跑版；正常和中斷後都找得到下一步；數字能回查，錯誤、零、缺值和結果未知不混淆。

## 2. 架構取捨

保留 Admin 與 POS 兩套 React／Vite 介面，及同一套 Express／Prisma／PostgreSQL 模組化單體；前端可不同，資料與正式過帳只有一個權威。先不上微服務、先不換 ERP，不新增全站共用 UI 套件。沿用 [ADR-012](https://github.com/skydreamer0/startup/blob/d703e416952b0e02a8241a86057d248a5c7b4662/systems/enterprise-admin/infrastructure/adr/adr_012_shared_ui_library_decision.md) 的實際重用門檻。

- 借 **Odoo** 的接收／隔離／上架分段，但單店一般收貨不用每批都按三次確認。[Odoo 收發貨](https://www.odoo.com/documentation/19.0/applications/inventory_and_mrp/inventory/shipping_receiving/daily_operations.html)
- 借 **ERPNext** 的單據與過帳分離、實收／拒收分列，以及原始帳保留、用反向項更正。不照抄關班才寫庫存帳的模式。[ERPNext 收貨](https://docs.frappe.io/erpnext/purchase-receipt)・[不可變帳](https://docs.frappe.io/erpnext/immutable-ledger-in-erpnext)
- 借 **Shopify** 的櫃台優先動作與能力降級提示、**Liberty** 的藥事覆核與收銀分工。不照搬雲端同步、離線卡支付風險或美國合規流程。[Shopify 離線](https://help.shopify.com/en/manual/sell-in-person/shopify-pos/selling-offline/offline-features)・[Liberty](https://libertysoftware.com/pharmacy/)
- 借 **HPK** 一區一個主要操作、同排按鈕等高、焦點、短篩選與搜尋組字規則。不搬品牌色、導航、資料、Base UI 依賴或實作原碼。

## 3. 功能需求與不變條件

### R1 工作台、角色與資料狀態
工作台先呈現需處理、待核對、可續作三類任務，跨日草稿也能找到。管理導覽主列：工作台／銷售／收貨／商品庫存／營運，設定另置。待確認不得標成完成；讀不到不能顯示為零。角色切換後，舊資料或草稿不可跨帳號出現。

### R2 收貨、批次、隔離與上架
收貨單 → 私人草稿 → 對照品項及包裝 → 核對實收、差異、批號、效期 → 依權限正式過帳 → 確認庫位；入庫、可售、付款、印標籤分開。單據 10 盒、實到 8、其中 1 隔離的驗收，畫面及紀錄需分開說明短少 2、隔離 1、可售 7；未知品項不得自動放行。照片／OCR 只產生候選，不能自行寫入產品主檔或完成入庫。同一請求只過帳一次；關窗後能恢復原草稿與差異。

現況：主線已有私人草稿 (歷史 #153) 和獨立的初次批次收貨，兩者不是同一條正式收貨流程。[#209](https://github.com/skydreamer0/startup/pull/209) 隔離驗收在 Draft 上通過，不是正式入庫或門市上線證據。

### R3 商品、庫存和實物流
以商品／包裝、批號、庫位辨識；條碼多筆相符須人工選，不能默默取第一筆。實體量、隔離量、保留量、可售量分開。近效期優先只從合格批次建議，不越過隔離／放行。退回、移位、盤點差異各有原因與可追溯流水；不靠直接改餘額修帳。退款不自動代表實物已回庫。

### R4 POS、付款與中斷復原
查找／掃碼、辨識、加車、核對、提交付款為不同動作。搜尋和掃碼的 Enter 不提交付款；同碼多筆不能自動入車。桌面左商品右購物車；會員／人員跟購物車，合計和前往付款在主操作區。窄版可換「商品／購物車」，仍保留件數合計。交易結果不明，保留原命令及購物車狀態，只提供查回原交易；不能自動另建交易。列印失敗只補印或查印件狀態，不重做結帳或入庫。

### R5 交班、營運與對帳
報表明示期間、資料時間、來源與是否估算。歷史毛利用當時成本；真正結清、退款及實物流分別記錄再對帳。不把成功空資料、真零、失權、讀取失敗與舊資料混成同一狀態。關班結果與正式交易、支付、退款和庫存流水可互相核對。

### R6 前端尺度、觸控與可及性
用 1366×768、1024、平板橫／直向與 390px 作三張代表頁的設計檢查；空間不足重排，不縮整頁或藏必要資料。POS 主要觸控目標 44–48 CSS px（產品目標），共用控制須有清楚名稱與焦點；鍵盤、掃碼槍、中文組字、長品名、縮放和軟鍵盤分開驗。收貨寬版原單與核對並排，窄版切換並保留同一列；商品庫存先呈現辨識、規格、包裝、庫存及狀態，批號、來源和編輯在詳情，不犧牲返回位置。

### R7 本地部署、設備與資料
外網斷但店內 API 還在，跟店內 API 也斷，是兩種情境。後者不得宣稱還能完成正常扣庫結帳。測試先用假資料；店內資料、處方、健保、外部支付與硬體需另具合適授權和驗收。可監控資料庫、儲存、備份、復原、設備狀態，備份存在不等於還原成功。

## 6. 基本架構就緒後｜第一階段介面改善

**目標：把店員每天真的會碰到的收銀、收貨草稿及商品查找做成可操作、可續作的工作畫面。** 第一階段不以全站同時換皮為成功，也不以藥師工作台、正式過帳、OCR 或帳務功能已上線為成功。

**開工條件：** 核對當前精確合併基準、Admin／POS 真正入口、現行權限、既有讀寫契約及測試方式。與 [#199](https://github.com/skydreamer0/startup/issues/199) 的 shell 前置對齊；若前置還沒過，只能做畫面盤點、線框、純展示和既有操作的有界試點，不啟用新的導覽或業務寫入。若已有同範圍候選則沿用，不重做。

| 順序 | 第一階段要改善什麼 | 做到哪裡可驗收 |
|---|---|---|
| **1.1 現況與尺度** | 對照真 Admin／POS 的收銀、收貨草稿、商品清單，非兩個 POS 原型。記窄版與 iPad 橫直向的擁擠、溢位、鍵盤遮擋與操作順序。定字級、欄位優先權、主要按鈕和提示的共同規則。 | 每頁有同一版本的現況、提案與降欄規則。1366×768、1024、iPad 直／橫、390 CSS px 不裁切主要操作；長中文可讀，縮放與鍵盤另驗。 |
| **1.2 控制項試點** | 後台用報表舊資料／重試；POS 用條碼提示／手動貼碼。共用主次、狀態、焦點與忙碌規格，先各自實作，不抽全站套件。 | 重試只有一個在途唯讀請求，不清掉條件；空資料、真零、讀不到、舊資料與失權分開。貼碼、核對、多筆選擇及取消可用，IME／掃碼 Enter 不觸發背景加車或付款。 |
| **1.3 收銀工作區** | 左側搜尋與結果，右側購物車、會員與交易摘要；合計和前往付款留在可達區。次要工具下放。窄版改商品／購物車切換但保留摘要。 | 找品、同碼多筆、掛單／回來、取消和交易結果未知能完成或安全接回；不改命令、金額、扣庫及付款契約。沒有實機就標未驗，不拿桌面模擬代替。 |
