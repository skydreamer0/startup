# 系統化除錯 (Systematic Debugging) 工作流

當使用者觸發此工作流時，遇到任何 Bug、測試失敗或非預期行為時，請嚴格執行以下 **「根本原因導向 (Root Cause Oriented)」** 的四階段流程：

## 🚨 鋼鐵禁令：嚴禁「瞎猜修復」
在完成「階段 1」的根本原因調查前，**絕對禁止** 提出任何修復方案。若無法穩定重現或缺乏證據，請優先加入探測日誌 (Diagnostics/Instrumentation)。

---

## 階段 1：根本原因調查 (Root Cause Investigation)
**在嘗試修復前，你必須：**

1. **詳讀報錯詳情**：包含 Stack Traces、檔案路徑、行號。不可略過任何警告。
2. **穩定重現 (Reproduce)**：建立最簡化 (Minimal) 的重現步驟。若無法重現，禁止猜測。
3. **檢查最新變更**：追蹤 Git Diff、套件更新、環境變數或配置檔案的變動。
4. **添加探測點 (Instrumentation)**：對於跨組件 (DB -> API -> UI) 的問題，在各層邊界加入 Log，追蹤數據流 (Data Flow) 直到發現錯誤源頭。

## 階段 2：模式分析 (Pattern Analysis)
1. **尋找正常範例**：在專案中找出類似功能的正確寫法。
2. **對比差異**：列出壞掉的部分與正確範例的所有微小差異，不要假設「這應該沒差」。
3. **理解依賴**：分析該功能依賴的配置、權限、或環境設定。

## 階段 3：假說建立與驗證 (Hypothesis & Testing)
1. **單一假說**：明確宣告「我認為根本原因是 X，因為 Y」。一次只驗證一個假說。
2. **極簡測試**：進行最微小的變動來驗證假說，不要一次改多個變數。
3. **失敗則停止**：若假說錯誤，復原變更，重新回到階段 1。

## 階段 4：實作與驗證 (Implementation)
1. **建立失敗測試 (Failing Test)**：在修復前，必須有一個測試案例能反應此 Bug。
2. **單一修復**：僅針對根本原因進行修復，**不准** 在此時進行順便的重構或「我順便改了 X」。
3. **斷後驗證**：確保 Bug 已解，且沒有引入 Regression。
4. **架構質疑**：若同一個 Bug 嘗試修復 **3 次以上均失敗**，停止修復，與使用者討論是否為架構性問題，需重新設計。

---
> [!IMPORTANT]
> **紅燈警報**：如果你發現自己在說「試試改這個看看會不會動」、「我猜可能是 X」，請立即停止並回到階段 1。
